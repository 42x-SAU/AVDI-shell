# План реализации: Redis, WebSocket и улучшения очереди задач

## Обзор проекта
AVDI (система диагностики) - это распределенная система, состоящая из:
- **Сервер** (Go, HTTP API) - управляет агентами, задачами и результатами
- **Агенты** (Go) - выполняют диагностические проверки (checks)
- **PostgreSQL** - основное хранилище (агенты, задачи, результаты)
- **Очередь на PostgreSQL** - текущая реализация через `FOR UPDATE SKIP LOCKED`

## Цели реализации
1. **Real-time обновления статусов** через WebSocket
2. **Ограничение одновременных задач на агента** (конфигурируемое)
3. **Повторный запуск задач при временных ошибках** с экспоненциальной задержкой
4. **Интеграция Redis** для очереди, кэша и pub/sub

## Архитектурные изменения

### 1. Добавление Redis
```
+----------------+      +----------------+      +----------------+
|    Сервер      |      |     Redis      |      |   PostgreSQL   |
|                |------|                |------|                |
| - WebSocket    |      | - Pub/Sub      |      | - Основные     |
| - Ограничения  |      | - Rate limiting|      |   данные       |
| - Повторы      |      | - Кэш статусов |      | - Задачи       |
+----------------+      +----------------+      +----------------+
```

**Redis будет использоваться для:**
- **Pub/Sub каналы** для real-time уведомлений
- **Rate limiting** для ограничения одновременных задач
- **Кэширование статусов** агентов и задач
- **Очередь отложенных задач** для повторных попыток

### 2. WebSocket сервер
- **Эндпоинт**: `/ws` (upgrade с HTTP)
- **Аутентификация**: через токен агента или API ключ
- **Подписки**: клиенты могут подписаться на:
  - `agent:{id}` - статус конкретного агента
  - `task:{id}` - статус конкретной задачи
  - `broadcast` - все обновления
- **Сообщения**: JSON формата:
  ```json
  {
    "type": "task_updated",
    "data": {
      "task_id": 123,
      "status": "running",
      "agent_id": 456,
      "timestamp": "2024-01-01T12:00:00Z"
    }
  }
  ```

### 3. Система ограничения одновременных задач
**Текущая проблема**: Агент может взять неограниченное количество задач одновременно.

**Решение**: Использовать Redis для отслеживания активных задач на агента.

**Алгоритм**:
1. При запросе следующей задачи (`/agents/tasks/next`):
   - Проверить в Redis текущее количество активных задач агента
   - Если `active_tasks >= max_concurrent` (настраиваемо), вернуть 429
2. При старте задачи увеличить счетчик в Redis
3. При завершении задачи уменьшить счетчик

**Конфигурация**:
- `MAX_CONCURRENT_TASKS_PER_AGENT` (по умолчанию: 3)
- Настраивается через переменные окружения или конфиг агента

### 4. Механизм повторного запуска задач
**Текущая проблема**: Задачи с `max_retries > 0` не перезапускаются автоматически.

**Решение**: Система отложенных задач через Redis Sorted Sets.

**Алгоритм**:
1. При неудачном выполнении задачи (exit_code != 0):
   - Если `retry_count < max_retries`:
     - Вычислить задержку: `delay = base_delay * (2^retry_count)`
     - Добавить задачу в Redis Sorted Set с score = `now + delay`
     - Увеличить `retry_count` в PostgreSQL
2. Фоновый воркер проверяет Sorted Set и возвращает задачи в очередь

**Конфигурация**:
- `BASE_RETRY_DELAY_SECONDS` (по умолчанию: 30)
- `MAX_RETRY_DELAY_SECONDS` (по умолчанию: 3600)

## Детальный план реализации

### Фаза 1: Подготовка инфраструктуры
1. **Добавить Redis в docker-compose.yml**
   ```yaml
   redis:
     image: redis:7-alpine
     ports:
       - "6379:6379"
   ```

2. **Обновить go.mod с зависимостями**
   ```bash
   go get github.com/redis/go-redis/v9
   go get github.com/gorilla/websocket
   ```

3. **Создать конфигурацию Redis**
   - Файл `internal/redis/client.go`
   - Поддержка переменных окружения `REDIS_URL`

### Фаза 2: WebSocket сервер
1. **Создать WebSocket обработчик** (`internal/server/websocket.go`)
   - Upgrade соединения
   - Управление подключениями (hub pattern)
   - Рассылка сообщений

2. **Интегрировать с существующим сервером**
   - Добавить маршрут `/ws`
   - Модифицировать `Server` структуру для хранения hub

3. **Добавить отправку событий**
   - При изменении статуса задачи
   - При heartbeat агента
   - При создании новой задачи

### Фаза 3: Ограничение одновременных задач
1. **Создать Redis-based rate limiter** (`internal/queue/limiter.go`)
   - Использовать Redis INCR/DECR с TTL
   - Ключи: `agent:{id}:active_tasks`

2. **Модифицировать `GetNextTask` в `pgqueue.go`**
   - Проверять лимит перед выдачей задачи
   - Увеличивать счетчик при успешной выдаче

3. **Модифицировать `CompleteTask`**
   - Уменьшать счетчик при завершении задачи

### Фаза 4: Повторный запуск задач
1. **Создать Retry Manager** (`internal/queue/retry.go`)
   - Redis Sorted Set для отложенных задач
   - Фоновый воркер для проверки

2. **Модифицировать логику завершения задач**
   - При неудаче проверять `max_retries`
   - Добавлять в отложенную очередь

3. **Добавить API для ручного перезапуска**

### Фаза 5: Интеграция и тестирование
1. **Обновить docker-compose для тестирования**
2. **Создать тестовые сценарии**
3. **Проверить обратную совместимость**
4. **Обновить документацию**
